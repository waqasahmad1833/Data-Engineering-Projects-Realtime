# Capacity planning: 30+ TB/month

All per-event numbers below were **measured** on events from the project's simulator
(see "How the numbers were measured"). Ratios on real exchange traffic will differ;
re-measure with `scripts/validate_sql.py`-style sampling before ordering hardware.

## Inputs

| Quantity | Value | Source |
|---|---|---|
| Raw ingest target | 30 TB/month = **1.0 TB/day** (design for 1.2 TB/day) | requirement (+20% headroom) |
| Average raw JSON event | **423 bytes** | measured, 400k events |
| Event mix | 73.8% bids, 25.8% impressions, 0.39% clicks, 0.02% conversions | simulator (35% win rate, 1.5% CTR, 6% CVR) |
| Diurnal peak / average | 3x | typical RTB traffic shape |

## Throughput

| | Average | Peak (3x) |
|---|---|---|
| Events/day | 1.0e12 B / 423 B = **2.36 billion** | |
| Events/second | **27,400** | **82,000** (design: 100k at 1.2 TB/day) |
| Raw bytes/second | 11.6 MB/s | 35 MB/s |

## Kafka

| Item | Calculation | Result |
|---|---|---|
| Compression (zstd-3, ~1 MB batches) | measured | **5.2x** |
| Stored per day | 1.0 TB / 5.2 | 190 GB |
| Retention 3 days x RF 3 | 190 GB x 3 x 3 | **1.7 TB** cluster-wide |
| Brokers | 6 x 1 TiB (≈ 3.5x headroom over 1.7 TB) | `k8s/kafka.yaml` |
| Partitions (`ad.events`) | 48 = Flink source parallelism; ≈ 570 ev/s avg per partition | `k8s/kafka-topics.yaml` |

Ingress (35 MB/s raw at peak, ~7 MB/s on the wire after compression) is far below what
6 brokers sustain; brokers are sized for retention, replication and rebalancing headroom.

## Flink

| Item | Calculation | Result |
|---|---|---|
| Parse + validate + serialize | measured on one core | **~270k events/s/core** |
| Parsing CPU at 100k ev/s peak | 100k / 270k | < 1 core |
| Dedup state (1 h TTL) | 27.4k ev/s x 3600 s x ~80 B/key (RocksDB) | **~8 GB** avg, ~24 GB at sustained peak |
| Attribution join state (30 min of impressions) | 7.1k imp/s x 1800 s x ~600 B | **~7.7 GB** avg, ~23 GB at peak |
| Spend windows | 500 campaigns x a few windows | negligible |
| Layout | 12 TaskManagers x 4 slots (4 vCPU, 16 GiB) = parallelism 48 | `k8s/flink.yaml` |

Parsing is cheap; the budget goes to keyed shuffles (dedup, join), RocksDB state
(~50 GB worst case across 48 subtasks ≈ 1 GB each) and checkpointing to S3.
Incremental RocksDB checkpoints keep each checkpoint to the changed SST files.

## ClickHouse

### Storage

| Item | Calculation | Result |
|---|---|---|
| Compressed size per row | measured (UUID columns dominate: ~33 of 58 B) | **58 B/row** |
| Raw JSON → ClickHouse | 423 / 58 | **7.3x** |
| Per day, per replica | 2.36e9 x 58 B | **137 GB/day** (≈ 4.1 TB/month) |
| Hot tier (7 days, NVMe) | 137 GB x 7 | 0.96 TB per replica set → **240 GB per node** (4 shards) |
| Cold: bids (30 days total) | 137 GB x 73.8% x 23 days | 2.3 TB |
| Cold: other events (180 days total) | 137 GB x 26.2% x 173 days | 6.2 TB |
| Cold total (S3, steady state) | (2.3 + 6.2) TB x 2 replicas | **≈ 17 TB** (≈ $390/month at $0.023/GB-month) |

Each node has 2 TiB NVMe: 240 GB of hot data plus space for merges (a merge temporarily needs
the size of its inputs), the 200 GiB S3 read cache, rollups and growth to ~2x volume.

### Write path

| Item | Value |
|---|---|
| Sink writers | 4 shards x 2 writers/shard = 8 subtasks |
| Rows per writer (avg) | 27.4k / 8 ≈ 3.4k rows/s |
| Flush | every 5 s or 100k rows / 64 MB → ≈ 17k-row batches at average load |
| Inserts per shard | 2 writers / 5 s ≈ **0.4 inserts/s** (ClickHouse guideline: ≤ 1/s per table per shard) |
| HTTP body compression | gzip, measured **4.9x** |

Ingest alone would fit on 2 shards; 4 shards are chosen for hot-tier capacity, merge
bandwidth, and query parallelism on the raw table.

### Nodes

| Role | Count | Spec |
|---|---|---|
| ClickHouse | 8 (4 shards x 2 replicas) | 32 vCPU, 128 GiB RAM, 2 TiB NVMe |
| ClickHouse Keeper | 3 | 4 vCPU, 16 GiB, 50 GiB SSD |

## Scaling levers (in order of cost)

1. **Longer hot window / more data**: larger NVMe or move to cold sooner (TTL `TO VOLUME`).
2. **More Flink throughput**: raise parallelism via savepoint upgrade (partitions allow up to 48;
   add partitions first beyond that).
3. **More insert throughput**: raise `SINK_WRITERS_PER_SHARD`; keep inserts/s per shard ≤ 1.
4. **More query capacity**: add replicas (read scaling, no data movement).
5. **More shards**: new shards with the same sharding key; see the runbook for rebalancing.

## How the numbers were measured

- Event size and mix: 400,059 events generated by `generator/src/adgen/simulator.py`.
- ClickHouse compression: the same events loaded into `ad_events_local` (schema from
  `infra/clickhouse/schema/02_ad_events.sql`) in embedded ClickHouse, then `OPTIMIZE FINAL`,
  reading `system.columns`.
- Kafka and HTTP compression: zstd level 3 on a ~1 MB batch and gzip level 6 on newline-delimited JSON.
- Flink parse throughput: `AdEventParser` + `AdEventRowMapper` in a tight loop on one core (JDK 21).
